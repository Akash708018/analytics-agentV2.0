# F11 — An end-to-end browser suite in the repo, and a large-file check

Date: 2026-10-02. Branch: **main**. Owner: Claude Code. The user, asked whether to add a
Playwright test suite to the repo (D-F7-3): "yes go ahead". Logged as D-F11-1.

## Why

F2–F10 each checked the screens in a real browser against the real backend, with one-off
scripts kept outside the repo (D-F2-1, D-F7-3). They caught what AppTest cannot see: C12, C13,
the F9 selectors and the caption contrast. But nobody can re-run them. F11 puts those checks
in the repo as a suite anyone can run in one command.

## Scope

1. **The tool.**
   - `@playwright/test` **1.56.1**, a dev dependency in `frontend/package.json`. It is pinned to
     the Playwright this container ships, whose Chromium (build 1194) is preinstalled, so
     nothing is downloaded here.
   - Elsewhere: `npx playwright install chromium` once.
   - No Python dependency is added.
2. **The harness** (`frontend/e2e/servers.js`, Playwright's global setup). It starts, on free
   ports:
   - the real backend with a scripted model (`frontend/e2e/scripted_backend.py`, the
     `ScriptedLLM` seam the backend's own tests use), on an empty temporary state dir;
   - Streamlit pointing at it.

   It waits for both and stops both afterwards. Their logs are kept on failure. Set `E2E_APP`
   and `E2E_API` to use servers that are already running.
3. **The tests.** Each makes its own session and workspace through the API, so tests are
   independent and can run in parallel. Every value the page shows is checked against the
   API's own reply, never a constant.
   - **F2.** Start a session; a saved name survives a reload; every sidebar link keeps the sid;
     bad and unknown links; two tabs → conflict → Load latest.
   - **F3.** Upload in the browser → profile; Clean: tick, apply; Domain: confirm; Contract: fill
     the form, confirm.
   - **F4, F7.** Metrics: approve; validity rules: apply; Tools: a run equal to the API's run;
     the figures CSV equal to the result's figures.
   - **F5.** Ask: an answer with its plan and evidence; a reload does not resend.
   - **F6, F10.** Keyword groups: propose, approve, withdraw.
   - **F8.** A result's lineage equals the stored result; its rows on Results equal `inspect`.
   - **F9.** The stylesheet is on the page once; with reduced motion nothing animates.
   - **F10.**
     - A refused upload answered with the reader's guess;
     - the contract in force;
     - the cleaning losses and SQL;
     - a declared optional param;
     - an Explore run and a report, each equal to the API's.
   - **Large file.** A generated CSV of several hundred thousand rows uploaded through the
     browser. The profile's row count equals the API's, and each step's time is recorded.
4. **Run:**
   - `npm run e2e --prefix frontend` runs the suite.
   - The pytest suite is unchanged and stays the fast check.

## Expected results, stated before running

- `frontend/tests` (pytest): **289 passed**. F11 changes no Python file the tests import.
- The e2e suite: every test passes on the real backend. The expected count is fixed once the
  files are written (stated below, before the first full run).
- **Large file.** The upload, read and profile finish inside the test's limit. The page's row
  count equals the API's.
- **Upload cap.** The cap a person meets is Streamlit's (`server.maxUploadSize`, 200 MB by
  default), not the backend's (a CSV warns at 500 MB and is refused at 5 GB; scaled by RAM).
  The test records what the page says at that size; whether to change the cap is a decision,
  not part of this milestone.

## What was built

`frontend/e2e/`:

| File | What it holds |
|---|---|
| `playwright.config.js` | 3 workers, fully parallel; trace and screenshot kept on failure (`e2e/test-results/`, gitignored) |
| `servers.js` | Global setup and teardown. It starts the backend (`uv run uvicorn --factory scripted_backend:make`, empty `AA_STATE_DIR`) and Streamlit on free ports, waits for `/health` and `/_stcore/health`, and stops both. It then removes the workspaces the run made (read from the run's `sessions.db`; the engine keeps workspaces in `backend/workspace/`, which is not configurable). `E2E_KEEP=1` keeps logs and workspaces; `E2E_APP`/`E2E_API` reuse running servers; `E2E_PYTHON`, `E2E_WORKERS`. |
| `scripted_backend.py` | The real app with `ScriptedLLM`, the backend tests' seam. Routes and engine are real; only the model's words are fixed. |
| `helpers.js` | API setup (`adsReady`, `logisticsReady`, `keywordsReady`, `session`, `upload`, `remember`), and the page actions proven in F2–F10 (`choose`, `tick`, `type`, `keyed`, `multiselect`/`chips`, `eventually`). |
| `fixtures/` | `ads_messy.csv` (F3's synthetic ads, 11 rows, 1 duplicate) and `gsc_kw.csv` (F6's keyword file, written from the backend tests' gold keywords). Logistics and multiheader are read from `backend/tests/fixtures/`. |
| `*.spec.js` | 17 tests: session 3, prepare 1, metrics_tools 1, ask 1, keywords 1, results 1, f10 6, style 2, large 1. |

## Run

```text
npm run e2e --prefix frontend                     # all
npm run e2e --prefix frontend -- f10.spec.js      # one file; -g "<title>" for one test
E2E_LARGE_ROWS=2000000 npm run e2e --prefix frontend -- large.spec.js
```

Needs `frontend/.venv` (Streamlit), `uv sync` (the backend), `npm ci --prefix frontend`. Outside
this container, run `npx --prefix frontend playwright install chromium` once.

## Found on the way

1. **A backend bug:** [#24](https://github.com/Akash708018/analytics-agentV2.0/issues/24).
   - Two requests on one workspace at the same moment can answer 500: DuckDB's "Unique file
     handle conflict: Cannot attach … already attached" from `db.connect`.
   - The suite met it when a test read `/analyses` while the page was loading it. A plain
     backend reproduces it with 20 parallel GETs: 11, 4 and 7 of 20 answered 500 in three rounds.
   - People can meet it with two tabs on one session.
   - Filed for the backend, which owns the fix. Meanwhile the tests read the API before a page
     loads, and their GETs retry a 500 twice (POSTs never).
2. **Streamlit 1.64's multiselect is react-aria.**
   - Each chip is a `[data-tag]` span labelled with its value, and there is a "Clear all"
     button. `[data-baseweb="tag"]` finds nothing.
   - That is why F10's step 1b read `[]` while the screenshot showed the chips.
   - It is also why the first run of the prepare test left the proposed key column `cost` in
     place: the test counted 0 chips to delete, and the engine accepted `[cost, date,
     campaign]`. The test now clears with "Clear all" and checks the chips before and after.
3. **Races in the tests, not in the page.**
   - Streamlit draws a page in steps, and a run saves after it draws. So:
     - list assertions retry (`toHaveText([...])`, `expect.poll`);
     - reads of the saved session wait (`eventually`).
   - In 1 of 51 runs, a rerun from the previous answer closed a dropdown mid-choice. `choose`
     now closes it and chooses again (twice at most); every choice is checked against the API
     afterwards.
   - After these, 51 of 51 passed.
