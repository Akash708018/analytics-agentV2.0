## What the real backend does (probed before design)

The F3 messy CSV, cleaned, marketing confirmed, contract confirmed (7 forks answered):

- `GET /metrics/templates`: 6 available (CTR, CPC, CPM, CVR, CPA, ROAS), the rest unavailable
  (concepts missing). Approving CTR → `{ok, version: 2, measure: "ctr_ratio"}` (the file already
  has a `ctr` column). CPA → measure `cpa`. ROAS with `bindings: {}` → 422 `needs_data` "ROAS:
  no column is bound to 'conv_value'": the platform revenue basis needs a column the person
  names (`bindings.conv_value`).
- `GET /validity-rules`: 4 rules, all `suggested: true`, `approved: false`, `rows_affected` 0 or
  `null`. Approve adds, reject removes (`approved` reflects it on the next read).
- `GET /tools`: 70 = 45 active, 6 needs_domain, 19 needs_data. Core analyses are listed as
  active, but `POST /tools/core.trend/run` → **500** (KeyError; fixed as C11 → 422
  `not_a_domain_tool`).
- `GET /packs/{id}`: each tool's `description`, `params_required`, `slots` (e.g. `by: [channel,
  campaign]`); core has `festivals`.
- Runs: channel_efficiency → figures (`name, value, unit, provenance`), a bar series, caveats
  ("CTR: skipped -- metric 'ctr' is not approved…" until approved; then CTR/CPA figures by
  group). roas_change_explainer → 422 `param_required` (`missing: [period, baseline]`).
  budget_pacing → figures with `value: null` (suppressed) and a `table` series. festive_compare
  → 422 `festival_dates_unconfirmed` with `dates` per year. creative_fatigue → 409
  `needs_data` (`missing_concepts`). Periods: `2026-09`, `2026-09-05`, or `a/b` ranges.

## Scope

1. **Metrics page**: templates (available first; unavailable say which concepts are missing),
   "Approve" per template, optional "name the column for a concept" bindings. 422s are answered
   in place: `ambiguous_binding` → pick a column; `forks_unanswered` → answer; `needs_data` → the
   message plus the binding form. Validity rules: ticks start from the server's `approved`,
   suggestions never pre-ticked. "Apply" approves the newly ticked and rejects the unticked.
2. **Tools page**: domain tools only (core analyses run through a turn). Active / needs a domain
   (link to Domain) / needs data (missing concepts). Choosing a tool shows its description,
   required params (typed inputs with format help), optional column slots. Run →
   result. 422s answered in place: param_required, forks_unanswered (options from the contract
   proposal → `POST /forks`), ambiguous_binding → `params.bindings`, festival_dates_unconfirmed
   (dates shown, explicit confirm).
3. **Result view** (a component F5 reuses): summary; figures exactly as returned (`null` shown
   as "suppressed"); provenance per figure; series plotted as given (`bar` with `sort=False`,
   `line`, `scatter`; `table`/`funnel`/`stacked_bar` as tables); caveats, validity filters,
   pack rules, the fork answers used, the figure check.
4. Drafts saved: rule ticks, chosen tool, tool params, bindings. Results stay in the browser
   (they are data); a refresh shows the params and a Run button, not stale figures.
5. **C11 (backend)**: core analyses via `/tools/{id}/run` answered 500; now 422.

### Findings

- **C11 (backend):** `POST /tools/core.trend/run` answered 500 (KeyError). Fixed; see above.
- **The Tools page could not answer `needs_data` for a concept.** The ROAS explainer needs
  `conv_value` bound for its own run (11). The runner accepts `params.bindings` as an override.
  "Name the column for a concept" is now a shared component on both pages, and the run sends it
  (11b; AppTest added).
- **Observation for the backend owner (not acted on):** a concept named while approving a
  metric (ROAS: `conv_value` → `revenue`) is not reused by tool runs on the same dataset, so the
  person names it twice. Remembering bindings per dataset would be a backend choice.
- Script-only: the first run counted charts before Vega drew them (0). A wait for 4
  `.vega-embed` nodes fixed the count; the charts were there.

Servers stopped after the run.
