## What the real backend does (probed before design)

Probed in-process (`make_env`, the B9 tests' harness) with the logistics fixture (492 orders)
and the keyword fixture:

- **Typed results.** `POST /tools/logistics.sla_compliance/run {by: hub}` returns:
  - `result_id` r_d9f5b2baa9d987b4, with `run_id` equal to it;
  - `status` ok, `snapshot` {hash e63766b0e708a9c4-492, rows 492};
  - `contract_version` 1, `grain` "one row = one order";
  - `metrics_used` {sla_breach: {measure: sla_breach}};
  - 41 figures and 2 series.

  Inside a turn, `run_id` is the turn id, and one of three results was `partial`.
- **Stored results.**
  - `GET /datasets/{id}/results` lists `{result_id, tool_id, run_id, status, created_at, stale,
    stale_reasons}`.
  - `GET /results/{id}` is the full result plus `stale` and `created_at`.
  - A corrected re-upload made both results stale ("the data changed (cleaning or a new upload)
    since this result"). Approving an unrelated metric (rto_rate) did not.
- **Inspection.** `GET /results/{id}/inspect` returns:
  - `step` "Breach rate", from `steps` ["Breach rate", "Breach rate by week"];
  - `headers` [hub, n, nulls, total, min, max, mean, median, stddev], with `rows` as strings;
  - `total_rows` 5, `rows_kept` 5, `rows_in_engine_output` 5.

  `sort_by` + `descending` + `limit` work. `sort_by=nope` → 422 `unknown_column` (`columns`
  listed). An unknown id → 404.
- **Value matching** (`logistics.sla_drivers`, `params.focus`):
  - "pune" → 422 `ambiguous_value` {param focus, column hub, candidates [PUNE_CENTRAL, PUNE_EAST,
    PUNE_SOUTH, PUNE_WEST]}.
  - "nagpur" → 422 `unknown_value` {values […]}.
  - "south" → 200 with the caveat "'south' read as hub = PUNE_SOUTH."

  **The tool spec does not declare `focus`.** It appears only as `focus_param: focus` in its
  step filters, so the F4 Tools page never offered it.
- **Pre-fill.** A second upload of the same export into the same workspace gets
  `proposal.prefill`:
  - `{from_dataset_id, from_name, similarity 1.0, contract_version}`;
  - `contract` {grain, primary_key, date_column, measures, dimensions, aggregations,
    measure_definitions};
  - `fork_choices`, `domains`, `metrics`, `validity_rules` and a `note`.

  No window is included; the backend says the window must be set for this file.
- **Routing and blocked plans.**
  - With no metric approved, "Which hub is worst on SLA…" gives a `plan` {playbook
    sla_where_and_why, steps [], routed_by rules, blocked ["the approved metric 'sla_breach'"],
    recovery "Approve the SLA breach metric (metrics screen: …)"}.
  - The answer has `blocked` set, 0 model calls and 0 tool calls.
  - With metrics approved, the plan has `routed_by: rules` and three steps.
- **Carry-forward.**
  - The run meta gains `embedding_version` {embedding, dims, dims_note, normalisation, input,
    generation 0c71d089bb46} and `carry_forward`. Before any approval it reads {status
    "nothing to carry", suggested 0}.
  - After approving "sushi delivery pune"'s group and re-uploading with 2 new phrasings, the
    rerun gives `carry_forward` {status ok, suggested 1, note}. It also gives a proposal
    "sushi · delivery (new keywords)" with `joins` = the approved group's id and keywords
    [sushi delivery wakad, sushi delivry aundh].
  - The backend's own test accepts it by `merge [approved id, proposal id]`, and the result
    stays approved.

## Scope

1. **Results view** (Tools, Ask Evidence, the new Results page).
   - Each result's status is shown: "partial: a step was skipped or refused" or "insufficient
     data: no reportable figure".
   - Its lineage, as returned: rows and snapshot hash, contract version, grain, metrics used,
     result id.
   - A link to page through its rows on Results.
2. **Results page** (new, after Tools).
   - The dataset's stored results, each with its tool, status, time and staleness. The person
     picks one (no default); the choice is saved, ids only.
   - The full result renders. A stale result says why, every reason as returned.
   - "Every row": step, sort column, order, a group filter, and page size and offset. Rows are
     shown exactly as the engine returned them.
3. **Ask Evidence.** The plan says whether rules or the planner chose the playbook. A blocked
   plan shows what is missing and the backend's recovery, with links to the screens it names.
4. **Keyword groups.**
   - Proposals that `join` an approved group are listed first. Each says that accepting adds
     its keywords to that approved group, and approves them; the button sends
     `merge [approved, proposal]`.
   - The run line shows the embedding generation and the carry-forward status (ok / nothing to
     carry / disabled with its reason).
5. **Contract pre-fill.**
   - The similar dataset's answers are shown with where they come from and how alike the
     columns are.
   - "Use these answers" fills only fields the person has not answered: grain, key, roles,
     aggregations, definitions, fork answers.
   - Its domains, metrics and validity rules are listed with links; they are not applied here.
   - The window stays the person's.
6. **Tools.**
   - Optional params a pack tool reads (`focus_param` in its steps) are offered, blank.
   - `ambiguous_value` offers the candidates and `unknown_value` the known values, none
     selected. The person picks one and runs again.

## Expected results, stated before running

- Unit:
  - The optional params read from a pack spec give `["focus"]` for sla_drivers and `[]` for a
    tool without filters.
  - The pre-fill mapping fills only unanswered fields. It turns
    `date_column`/`measures`/`dimensions` into roles, and fork answers the proposal does not
    offer are dropped.
  - The lineage line holds the backend's values.
- AppTests (fake, shapes as probed):
  - Results lists the stored results with nothing selected. Choosing one renders it; a stale
    one shows its reasons.
  - Inspect sends `step` / `sort_by` / `descending` / `limit` / `offset` exactly as chosen. A
    422 `unknown_column` shows the backend's message.
  - A blocked turn shows "Blocked" with the recovery text.
  - A `joins` proposal sends `merge [approved, proposal]`.
  - Pre-fill leaves an answered grain alone and fills the rest.
  - `ambiguous_value` offers 4 candidates, none selected; picking one and running sends it as
    `focus`.
- Browser (real backend, logistics fixture):
  - A Tools run shows status and lineage equal to the API.
  - Results lists it and pages its rows, and the rows equal `inspect`. After a corrected
    re-upload, the result says it is out of date.
  - focus "pune" offers the 4 hubs.
  - A second upload shows the pre-fill from the first.

## What was built

- `frontend/views/results.py`, the **Results** page (registered in `state.PAGES`,
  `app.TITLES` and `shell.STEPS`; the draft gains `result`).
  - The stored list, with "N stored · M out of date".
  - A selector with no default. A result's own link (`?result=r_…`) selects it once, then the
    parameter is dropped.
  - The result rendered in full, then "Every row": step, sort, largest first, a group filter,
    rows per page, and previous/next. Rows are shown as returned, with the backend's counts.
- `components/results.render_result(result, key, link=True)`:
  - an "Out of date: …" warning with every reason;
  - the status note (partial / insufficient data);
  - the lineage line (`prep.lineage`);
  - a link to the rows.
- `components/evidence`: a plan says "chosen by its question patterns, no model call" (rules) or
  "chosen by the model" (planner). A blocked plan reads "⛔ blocked: needs … " + the backend's
  recovery. A blocked answer says nothing was run.
- `views/keywords.py`:
  - "New keywords for approved groups", each with "Add to '<group>'", which sends
    `merge [approved, proposal]`;
  - the run line shows the generation and the carry-forward status; a disabled one shows its
    reason;
  - the list notes "proposed to join …".
- `views/contract.py`: "Answers from a similar file". "Use these answers (N you have not
  answered)" goes through `prep.prefill_answers`. The file's domains, metrics and rules are
  listed and not applied.
- `views/tools.py`:
  - optional params from `prep.optional_params` (Focus on, blank);
  - `ambiguous_value` / `unknown_value` offer the backend's values as a radio with no
    selection; the pick fills the param.
- `frontend/tests/fake_backend.py`: stored results with lineage, list/get/inspect (with a query
  log), `make_stale`, `prefill`, `logistics.sla_drivers` with `focus` and its value errors,
  and `block_turn`.
- api-request [#23](https://github.com/Akash708018/analytics-agentV2.0/issues/23): declare
  optional tool params instead of leaving them in step filters.
