## What the real backend does (probed before design)

The real app was run in-process (`TestClient(create_app(...))`) with the backend's own keyword
fixture (`backend/tests/fixtures_v2/keywords_gold.py`: 177 distinct search terms for a Japanese
restaurant in Pune, Hinglish and typos included; columns `row_id, date, query, page, clicks,
impressions, position`):

- `POST .../keyword-groups/run {}` before a domain is confirmed → 422 `needs_data` "no search
  term, query or keyword column". With `{"column": "query"}` it runs with or without a domain.
  No endpoint says which column the pack binds to the search-term concept before a run.
- `{"column": "nope"}` → **500** (DuckDB binder error escapes `KeywordService.run`). The UI
  only offers the profile's columns, so it cannot send this. It is reported for the backend
  owner, not fixed here.
- Run meta: `{column: query, embedding: chargram/tfidf-char2-4, threshold: 0.6, typos_merged:
  {japanise→japanese, japnese→japanese, raman→ramen, shushi→sushi, sushie→sushi,
  sushii→sushi}, keywords: 177, proposed_groups: 48}`. The 48 proposals are all `proposed_by:
  rules`, none approved. Sizes run from 14 keywords down to 1, with 25 single-keyword groups.
  Intents: commercial 18, informational 13, local 7, navigational 6, transactional 4. Facet
  names: dish, info, brand, area, price, near_me, delivery.
- `GET .../keyword-groups` lists approved groups first, then by group id. Keywords come back
  sorted.
- Actions (each returns the full listing):
  - approve: one or more ids.
  - rename: first id, `label` required.
  - merge: needs 2 or more ids, merged **into the first**, `label` optional.
  - move_keyword: first id is the source; needs `keyword` and `target_group_id`. A source left
    empty is deleted.
  - split: first id; `keywords` must be some, not all, of the group's keywords; `label`
    optional (default "<label> (split)").
- Approval follows the group a keyword lands in:
  - Merging into an approved group approves the merged-in keywords.
  - Merging an approved group *into a proposal* withdraws its approval.
  - Split-off keywords become a new proposal, even when split from an approved group.
  - Moving a keyword into an approved group approves it.
- There is **no action that withdraws an approval** (the enum is approve | rename | merge |
  move_keyword | split).
- Running again drops every unapproved group, including the person's renames and merges, and
  proposes afresh (new ids). Approved groups and their keywords stay (47 groups after one
  approval and a rerun). The pack tool `marketing.keyword_grouping` does the same run.
- Errors:
  - 422 `bad_action`: "group_ids needed", "rename needs label", "merge needs two or more
    group_ids", "keyword not in group, or no target group", and split's "some (not all)".
  - 404 `not_found`: "unknown group(s): [...]".
  - An unknown action name is FastAPI's 422 `detail`.
- `marketing.keyword_group_performance` before any approval → 422 `engine_refused` "no keyword
  groups are approved yet". After one approval it runs: a figure per approved group, plus
  "(ungrouped)" for the rest.

## Scope

A Keyword groups page, after Metrics and before Tools:

1. **Propose.** The person chooses the column holding the search terms; nothing is preselected,
   and the choice is saved in the session. The run's own record is shown: column, embedding,
   threshold, keywords read, proposals made, and typos merged.
   - If proposals exist, the button reads "Replace the N proposals" and says what is lost:
     renames, merges, moves and splits of unapproved groups. Approved groups stay.
2. **Review.** Each group shows its label, intent, keyword count, approval status, who
   proposed it, its facets, and every keyword.
   - A summary line counts groups, keywords and approved groups, and says only approved
     groups reach the engine.
   - Filters (status, intent, find a keyword) are browser-only view state.
3. **Approve.** Tick, then "Approve the N ticked". Nothing is pre-ticked. Ticks are saved
   (group ids only), and ticks for ids that no longer exist are ignored. The page says there
   is no way to withdraw an approval in API 0.6.0.
4. **Merge** two or more ticked groups. The person picks the group to merge into (no
   default). The UI states the backend's consequence before sending: the result is approved
   or a proposal, depending on the target, and it warns when an approved group would lose
   its approval. The request is sent as `[target, others…]`.
5. **Edit one group** (picked from a list, no default):
   - Rename it.
   - Split some keywords off; the UI says the split-off keywords become a new proposal.
   - Move one keyword to another group; the UI says when this approves or un-approves it.
6. **Tools.** On the Tools page, the keyword tools link here. `keyword_grouping` replaces the
   proposals. `keyword_group_performance` and `page_targeting` count approved groups only.

The page never computes figures; the counts are tallies of the listing the backend returned.

## Expected results, stated before running

- AppTests (stateful fake that copies the backend's action rules):
  - No column → Propose disabled and the column box is empty.
  - Choosing `search_term` and proposing sends exactly one `{"column": "search_term"}`. Every
    group renders with its intent, facets and `proposed_by`, and the typos merged are listed.
  - Nothing is ticked at first, and Approve is disabled. Ticking 2 sends `approve [a, b]`;
    both then read approved and the ticks clear.
  - Merging an approved group into a proposal shows the withdrawal warning and sends
    `[target, other]`.
  - Rename, split and move send the exact bodies. Split names the new proposal.
  - With proposals present, the run button reads "Replace the N proposals".
  - A `bad_action` / `not_found` reply shows the backend's message.
  - Ticks survive a refresh.
- Browser (real backend; domain and contract set up through the API, since F3 already checked
  that flow in the browser):
  - Upload the fixture and choose `query` → 48 proposals, the same as the API listing.
  - Approve one group, merge two, split one, move one keyword and rename one; the listing
    after each matches the API.
  - Tools → `keyword_group_performance` shows one "By group: <label>" per approved group,
    equal to the API's figures.
  - A refresh keeps the column and the ticks.

## What was built

- `frontend/views/keywords.py`, the Keyword groups page:
  - Propose: the column, then Propose (or "Replace the N proposals"); the last run's record and
    its spellings merged.
  - Groups: the summary, a link to Tools, ticked actions (approve; merge into a chosen group,
    with an optional name), "Edit one group" (rename, split, move a keyword), and the filtered
    list.
- `frontend/keywords.py`: the summary, facet text and filters, and the stated consequences
  (`merge_notes`, `move_note`, `split_note`), which follow the backend's rules as measured.
- Registration: `state.PAGES` and `app.TITLES` ("Keyword groups", between Metrics and Tools);
  `shell.STEPS`; `datasets.KINDS` gains `keywords`.
- `state._keywords`: the draft allowlist gains `keywords: {column, ticks{group_id: true}}`.
- `frontend/views/tools.py`: a note and link for `keyword_grouping` (replaces proposals) and for
  `keyword_group_performance` / `page_targeting` (approved groups only). A grouping run from
  Tools drops the cached listing.
- `frontend/tests/fake_backend.py`: keyword routes that copy `KeywordService` rule for rule
  (ordering, merge into the first id, split/move checks, error messages, a rerun keeping
  approved groups).
- api-request [#20](https://github.com/Akash708018/analytics-agentV2.0/issues/20): withdrawing
  an approval; the 500 on an unknown column.

  Step 7b shows the target surviving while 2 or more stay ticked.
- **Script slip: the split name box.** The multiselect's open list hid the page from role
  lookups; pressing Escape closes it.
