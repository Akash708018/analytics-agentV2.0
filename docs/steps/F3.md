## What the real backend does (probed before design)

A synthetic ad file with a duplicate row, `Google`/`google`/`google ` spellings and a `ctr` column,
against `uvicorn --factory backend.api.app:create_app` (`AA_NO_LLM=1`):

- Profile: 10 columns, one warning (`ctr looks like a per-row rate…`).
- Cleaning: `C001 DROP_DUPLICATE_ROWS` (lossy), `C002 TRIM_WHITESPACE utm_source` (lossless,
  `suggested: true`), `C003 NORMALISE_CASE utm_source` (lossy). Approving before the plan was
  fetched → 422 `refused` (`NO_CLEANING_PLAN`). **After applying C001+C002, the remaining action
  was renumbered `C001`.** A tick saved by id alone would now point at a different action.
- Detect: marketing 0.385, `confirmed: []`. Packs: core, logistics, marketing.
- Contract proposal: only `ctr` is a measure. cost/clicks/impressions/conversions/revenue come back
  as **dimensions**. `provisional`: grain, ctr's agg and definition, the analysis window; plain
  questions for each. 7 forks after marketing; 4 have no suggestion.
- Confirm with no fork answers → 422 `forks_unanswered` (`missing`). With forks but no aggregations
  → 422 `contract_provisional` (`provisional`, `questions` that name the engine's suggestion).
  Complete → `{ok, version: 1}`. The next proposal reflects the contract in force; 45 tools active.
- The proposal does not return measure definitions, the window, or the fork choices in force.

## Scope

1. **Data**: a profile table (values as returned) and warnings for the active dataset.
2. **Clean**: proposals as checkboxes, **none pre-ticked**. A "suggested" badge with its reason, an
   explicit "Tick the N suggested" button, lossy actions marked. "Apply" re-fetches the plan and
   sends only actions whose id+kind+column still match what the person ticked. Otherwise it asks
   for a review and sends nothing.
3. **Domain**: every pack except core, marketing first, with detection evidence. The ticks start
   from the server's `confirmed` list (the person's earlier choice) and are never guessed.
   Confirm sends the ticked list.
4. **Contract**: grain; a role per column (key/date/measure/dimension/ignore); per measure:
   aggregation (no default unless the proposal or the person has one), definition, "one value
   per"; window; caveats (the engine's are shown read-only); forks as radios with **no
   selection**, a suggestion + reason, and an explicit "Use the N suggested answers". Confirm
   maps the form to the API's names. 422s are shown as the questions they carry.
5. **Drafts saved** per dataset in `ui_state.drafts` (ticks, domain ticks, contract form, fork
   answers, the version confirmed here), so refresh/another tab keep half-done work.
6. **C8 fix**: `ui_state.datasets` becomes a list of ids (schema 2); names come from
   `GET /datasets/{id}`. F2's list of `{id,name,rows,columns}` objects hits the backend's
   data-row guard at 20 uploads (measured: `20 same-shaped objects look like data rows`). A name
   like `leads_9876543210` is refused as a phone number (measured). Schema 1 is migrated.

Not in F3: answering ingest layout questions (no endpoint: api-request), metrics/validity rules
and tool runs (F4), ratio measures and flag rates (no proposal fields for them).

## Expected results, stated before running

- Unit: schema-1 → 2 migration keeps every dataset id. 50 ids pass the backend's guard. Drafts
  are allowlisted per dataset and dropped for datasets no longer listed. A stale tick (id
  reused for another kind/column) is never sent. Form ↔ API mapping: roles → primary_key /
  date_column / measures / dimensions; empty aggregations omitted.
- AppTests (fake backend): nothing pre-ticked on Clean or in forks. "Tick suggested" ticks only
  suggested ones. Apply sends exactly the ticked ids; a renumbered plan sends nothing and says
  so. Domain confirm sends the ticks. Contract confirm surfaces `forks_unanswered` and
  `contract_provisional` questions, then succeeds and records the version. Every draft survives
  a fresh AppTest (refresh).
- Browser (real backend): the same messy file goes upload → clean (tick suggested + duplicate
  drop, apply) → confirm marketing → contract (roles changed, aggs, forks via "use suggested" +
  the rest by hand, confirm). A refresh mid-contract keeps every field. The backend then reports
  marketing tools active.
